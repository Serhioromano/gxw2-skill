# План: механизм обратной связи навыка (skill feedback loop)

> Статус: черновик для реализации
> Цель: добавить в навык `gxw2-st` механизм, при котором агент, обнаружив что сгенерированный им код некорректен, **автоматически создаёт GitHub issue** в репозитории навыка с описанием инцидента и рекомендацией по улучшению самого навыка. Идея — «навык учится на своих ошибках»: каждый реальный кейс, где reference-файл оказался неверным или недостаточным, превращается в actionable issue с готовым diff для справочника.

---

## 1. Идея (как это работает)

1. Агент работает по двухфазному workflow (Plan → Generate) и выдаёт код.
2. В процессе выясняется, что код неправильный: ошибка компиляции в GX Works 2, пользователь исправил код вручную, поведение ПЛК не совпало с ожидаемым, либо пользователь прямо сказал «навык ошибся».
3. Агент **диагностирует первопричину**: какой reference-файл/правило было неверным или отсутствовало (`references/DB/*.md`, `common-rules.md`, `csv-variables.md` и т.д.).
4. Агент формирует issue по шаблону и **создаёт его в репозитории навыка** через `gh issue create` (gh уже обязателен для `make publish`).
5. Владелец репозитория получает готовый кейс: код до → код после → root cause → рекомендация по правке справочника. Остаётся только применить изменения и выпустить версию.

Механизм — это **чисто markdown-инструкции в навыке + команды `gh`**, никакого нового серверного кода не требуется. Агент умеет выполнять команды bash; `gh` уже в dev-предпосылках репозитория.

## 3. Дизайн механизма

### 3.1. Триггеры срабатывания (когда агент обязан инициировать feedback)

- Пользователь сообщает об ошибке компиляции / runtime-ошибке GX Works 2 (код ошибки, `Error ...`).
- Пользователь вручную исправил сгенерированный `.st`/`.csv` — агент видит diff и понимает, почему правка верна.
- Пользователь прямо говорит: «навык написал неправильно», «это не работает», «в инструкции сказано иначе».
- Агент замечает противоречие между reference-файлом и фактом, подтверждённым пользователем/ошибкой компилятора.
- Одна и та же инструкция/правило дало ошибку во второй раз (первый раз — можно поправить код молча; второй — сигнал, что справочник системно неверен).

### 3.2. Анти-триггеры (когда НЕ создаём issue)

- Ошибка в задании пользователя (неверное ТЗ, неверный адрес устройства в запросе).
- Ошибка окружения (не та версия GX Works 2, не та модель ПЛК, чем отличается от заявленной совместимости).
- Правильный ответ уже есть в references — просто применяем его, issue не нужен.
- Инцидент уже описан в открытом issue (см. дедупликацию).
- Пользователь запретил отправку (см. режимы).

### 3.3. Шаблон issue (английский — язык репозитория)

Заголовок: `[skill-feedback] <краткое описание, ≤80 символов>`

Тело — обязательные секции:

```markdown
## Context
<!-- Задача пользователя: что просили сделать, какая модель ПЛК, какая версия навыка -->

## What the skill generated
<!-- Код .st / фрагмент .csv, который сгенерировал навык (минимальный воспроизводимый фрагмент) -->

## What was correct
<!-- Исправленная версия кода (как сделал пользователь / как должно быть) -->

## Root cause
<!-- Какой reference-файл / правило было неверным или отсутствовало:
     references/DB/{INSTR}.md, common-rules.md, csv-variables.md, ... -->

## Recommended skill change
<!-- Что именно изменить в навыке, чтобы это больше не повторилось:
     - файл, секция, строки
     - новое/исправленное правило
     - пример для examples/ -->

## Environment
- Skill version: 1.3.0
- FX model: FX3U / ...
- GX Works 2 version: ...
```

Labels: `skill-feedback` (+ `bug`, если код был сгенерирован, но не компилировался; `enhancement`, если справочник просто неполон).

### 3.4. Механика (команды `gh`)

```bash
# 1. Проверка дедупликации: ищем похожий открытый issue по ключевым словам
gh issue list --repo Serhioromano/gxw2-skill \
  --label skill-feedback --search "<2-3 ключевых слова>" --state open

# 2. Создание issue (тело — из шаблона, санитизированное)
gh issue create \
  --repo Serhioromano/gxw2-skill \
  --title "[skill-feedback] <краткое описание>" \
  --body "$(cat /tmp/skill-feedback.md)" \
  --label "skill-feedback" \
  --label "bug"
```

- Перед созданием агент сохраняет тело во временный файл и отдаёт его пользователю для просмотра.
- Если `gh` отсутствует / не авторизован → **не падать**: вывести готовый текст issue в чат с инструкцией «вставить вручную» (fallback, см. 3.6).

### 3.5. Санитизация (обязательна)

- Удалять идентифицирующую информацию: названия компаний, адреса, IP, имена клиентов.
- Код сокращать до минимального воспроизводимого фрагмента; комментарии пользователя не копировать.
- Не включать внутренние пути проекта пользователя.

### 3.6. Режимы отправки (рекомендация — полуавтоматический)

| Режим | Поведение | Когда |
|-------|-----------|-------|
| **Semi-auto (рекомендуется)** | Агент формирует issue и **показывает превью + просит подтверждение одним сообщением** («создать issue?»). | По умолчанию: защищает от шума, пользователь видит, что уходит в публичный репозиторий |
| **Full-auto** | Агент создаёт issue без подтверждения, но только после дедупликации и при явном подтверждённом факте ошибки. | Если пользователь сказал «отправляй всегда автоматически»; переключается флагом в запросе |
| **Manual fallback** | Агент выводит готовый текст issue (с пометкой `[skill-feedback]`) в чат. | `gh` недоступен или пользователь не хочет авто-отправку |

Переменная окружения для явного включения full-auto: `GXW2_FEEDBACK_AUTO=1` (необязательно; достаточно словесной инструкции пользователя).

### 3.7. Правила против спама

- **Один issue на инцидент**, не на каждую мелочь: мелочи (опечатка в комментарии) не отправляем.
- Сначала дедупликация по `gh issue list --search`.
- Не отправлять повторно то, что уже исправлено в последней версии навыка (агент проверяет версию из frontmatter).
- Если сомнение «это ошибка навыка или пользователя» → не отправлять, только упомянуть возможность в финальном ответе.

## 5. Этапы реализации

### Фаза 0 — решения (согласовать до кодинга)
1. Режим отправки по умолчанию: semi-auto или full-auto.
2. Создавать label `skill-feedback` в репозитории вручную (владелец) — gh не умеет создавать labels без прав; делается один раз через UI или `gh label create`.
3. Нужен ли `.github/ISSUE_TEMPLATE` (да, если хотим и ручные репорты).

### Фаза 1 — ядро механизма
1. Написать `references/feedback.md`.
2. Добавить секцию + строку on-demand в `SKILL.md`.
3. Проверить внутренние ссылки (относительные пути от `skills/gxw2-st/`).

### Фаза 2 — обвязка репозитория
1. `.github/ISSUE_TEMPLATE/skill-feedback.yml`.
2. README — секция «Reporting skill issues».
3. Создать label `skill-feedback` в GitHub (вручную, владелец).
4. CHANGELOG + Makefile test.

### Фаза 3 — проверка сценария (вручную)
1. Смоделировать инцидент: дать агенту задачу, где reference заведомо неполон, получить код, «сломать» его, убедиться что агент формирует issue с правильными полями.
2. Проверить дедупликацию (создать второй issue с тем же текстом — должен быть заблокирован).
3. Проверить fallback без `gh` (например `gh` в PATH нет → выводится текст).
4. `make test` — smoke.

## 6. Критерии приёмки

- [ ] При подтверждённой ошибке сгенерированного кода агент автоматически формирует issue по шаблону (все секции из 3.3 заполнены).
- [ ] В issue указана версия навыка (из frontmatter SKILL.md).
- [ ] Дедупликация: повторный инцидент с тем же root cause не создаёт дубликат.
- [ ] Санитизация: в issue нет имён клиентов, адресов, IP, полных путей пользователя.
- [ ] Без `gh` / без авторизации агент выдаёт готовый текст issue в чат, а не молчит.
- [ ] `make test` проходит; CHANGELOG обновлён; README описывает механизм.

## 8. Риски и как с ними обходимся

| Риск | Митигация |
|------|-----------|
| Спам / мусорные issue | Триггеры только при подтверждённой ошибке; дедупликация; semi-auto по умолчанию |
| Утечка кода пользователя | Обязательная санитизация (3.5); превью перед отправкой |
| `gh` нет у пользователя навыка | Fallback на вывод текста (3.6) — механизм деградирует мягко |
| Дубликаты при массовом использовании | `gh issue list --search` перед созданием; рекомендация объединять однотипные в один issue |
| Агент создаёт issue «на пустом месте» | Анти-триггеры (3.2): ошибка ТЗ/окружения — не наш кейс |
